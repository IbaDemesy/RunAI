# V2 : repères techniques

Le [README](../README.md#v2--préparer-une-course) décrit les modes, le lancement et
les limites. `RUNAI_MODE` accepte `live`, `demo`, `replay` ; sans ce réglage, le mode
est live, sauf compatibilité explicite `RUNAI_DEMO=1`. `.env` est chargé par
`runai/config.py`. La santé locale, sans requête fournisseur, est exposée par
`GET /api/health`.

## Cadrage et exécution

- `POST /api/framings`, puis `GET /api/framings/{id}` et
  `POST /api/framings/{id}/replies` : informations manquantes, choix du candidat et
  corrections. Une révision périmée est refusée (409).
- `POST /api/framings/{id}/confirm` avec `revision` et `idempotency_key` :
  `plan_launch` puis création de mission. Même clé de confirmation : même mission.
  L'ancien `POST /api/missions` répond 410 et ne lance rien.
- `GET /api/missions/{id}` : `mission.v2` ; `GET …/events` : SSE `events.v1`,
  reprise par `Last-Event-ID`. Les routes `…/pause`, `…/resume`, `…/cancel` pilotent
  les agents ; les commandes caméra restent locales et distinctes.
- Les questions humaines passent par `…/questions/{qid}/answer`. Les démarches
  santé/consentement/éligibilité restent manuelles, jamais une autorisation d'agir.

En live, la recherche de candidats utilise `LinkupCandidateSearch` et uniquement
`LINKUP_API_KEY` via `get_settings()`. H utilise `HLifecycle` avec les contrôles de
`RealAgentRun`. Gladia fournit uniquement la transcription. Demo et replay utilisent
une recherche limitée aux événements enregistrés correspondant aux critères ; leur
confirmation sans fixture sélectionnée est refusée.

## Journey et exports

Après confirmation, `GET /api/missions/{id}/journey` retourne le séjour partiel ou
complet et sa révision. Les exports `/api/missions/{id}/recap.html`, `.pdf`, `.ics`
acceptent `?revision=N` : les liens du shell utilisent le même snapshot pour les trois
formats. Révision inconnue ou séjour indisponible : 404 ; panne de rendu : 503.
Le PDF exige aussi le moteur Chrome/Chromium du renderer existant. Les snapshots
restent en mémoire et sont perdus au redémarrage.

`mission_journey.project_journey` lit les résultats finalisés dans
`StepResult.data.journey` (ou son `answer` structuré) : `race` pour l'inscription,
`hotel` pour l'hébergement, `home/outbound/return_trip/local_cost` pour le transport,
selon les modèles de `runai.journey`. Les preuves `quote`, `rules`, `race_sheet`
utilisent les modèles métier existants ; `chosen_options` et `entry_path_id` restent
des choix explicites. Aucun géocodage ni horaire n'est déduit du texte libre.
`bib_pickup_closes` reste une fermeture, pas un rendez-vous. Les questions
d'éligibilité ne sont jamais transmises à H comme autorisation.

## Shell

Les scripts Journey et voix sont servis localement ; `?mock=1` utilise l'API simulée
du shell et les fixtures de `/static/contract-fixtures/`, distinctes du mode backend
`RUNAI_MODE=demo`. MapLibre est chargé depuis un CDN épinglé avec SRI ; les tuiles
proviennent d'OpenStreetMap. Une panne de carte conserve la timeline accessible.
Le saut au kilomètre nécessite un moteur Flyover chargé avec un tracé ; sans lui,
la commande échoue explicitement. Ces dépendances graphiques externes ne sont pas
validées par les seuls tests hors ligne.
